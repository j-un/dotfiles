次の開発タスクを、計画先行・委譲実装ワークフローで進める。メインセッションは計画・オーケストレーション・レビュー・統合を担い、実装コード自体は書かない。

タスク: `/devflow` の後に続くユーザーメッセージ（またはこのターンの残り）。空なら、計画の前にタスク内容を聞く。

## Phase 1 — 計画（plan モード）

1. まだ plan モードでなければ、何よりも先に SwitchMode で `target_mode_id: "plan"` を呼ぶ。Cursor CLI で `agent --plan` / `--mode plan` から開始した場合も、すでに plan モードとみなす。
2. 必要に応じてコードベースを調査し、次の構造で実装計画を設計する:
   - 可能な限り独立したチャンクに分割する。2 つのチャンクが独立なのは、触るファイル集合が互いに素な場合のみ。
   - 各チャンクに自己完結の仕様を書く: 目的、対象ファイル、期待動作、制約、正確な検証コマンド。この仕様は、本会話にアクセスできないエージェントでも実行可能でなければならない。
   - 依存関係を明示する: どのチャンクが並列か、どれが直列必須か。
   - 全チャンクを **implementer** サブエージェント（`~/.cursor/agents/implementer.md`）に割り当て、難易度に応じてチャンクごとにモデルを記録する（2 段階のみ）:
     - `cursor-grok-4.6-xhigh`（デフォルト）— 非自明なもの全般: 仕様が明確な実装、アルゴリズム、並行性、微妙な状態、性能・セキュリティ重要なコード、デバッグ判断が要りそうなチャンク
     - `composer-2.5` — 機械的な編集のみ（リネーム、設定の微調整）
     迷ったら grok を選ぶ。composer は明らかに機械的な作業に限定する。
   - エスケープハッチ: タスクが意味のある 2 チャンク以上に分解できない場合は計画に明記し、メインセッションでの直接実装を提案する（それでも計画先行）。
3. 計画を提示するとき、計画の承認（および CLI で auto-run / `--force` / `--yolo` を有効にすること）により、並列エージェントが権限プロンプトで止まらない旨を伝える。

## Phase 2 — オーケストレーション（承認後）

1. TodoWrite ツールでチャンクを追跡する（`merge: true`、チャンクごとに 1 todo）。
2. チャンクごとに Task ツールで **implementer** サブエージェントを 1 つ起動する:
   - カスタム `implementer` エージェント（`~/.cursor/agents/implementer.md`）を優先する。Task が組み込み型しか出さない場合は `subagent_type: "generalPurpose"` を使い、implementer の運用ルールと報告形式を `prompt` に埋め込む。
   - そのチャンクの自己完結仕様を `prompt` にそのまま渡す。
   - Task の `model` は計画に記録したモデルを設定する（省略禁止 / inherit に頼らない）。
   - 独立チャンクは 1 メッセージで並列起動し、依存チャンクは直列で実行する。
   - 並列チャンクがワーキングツリーで衝突しうる場合は worktree 隔離を使う: `subagent_type: "best-of-n-runner"`（隔離 git worktree）、またはユーザーに `agent -w` での再実行を案内する。
3. 各レポートが返ってきたら、チャンクの diff を批判的にレビューする: 正しさ、仕様準拠、TESTING.md 遵守（`~/.claude/TESTING.md` またはプロジェクト相当）。非自明な修正は、メインセッションで直さず、同じエージェントを Task の `resume`（エージェント ID）で再開する。
4. エージェントが設計判断をエスカレーションした場合はメインセッションで決め、仕様を更新して再委譲する（resume または新規 Task）。

## Phase 3 — 統合と検証

1. 全チャンクが着地したら、プロジェクトのフル検証（ビルド、テスト、lint）を実行する。
2. 結合 diff の横断整合性をレビューするか、深いレビューとして `/opus-code-review`（または同等）を提案する。
3. ユーザーへ報告する: 何を作ったか、チャンクごとの結果、検証結果、残フォローアップ。

## ルール

- メインのコンテキストを薄く保つ: レビューに必要な場合を除き、実装ファイルをメインセッションに読み込まない — implementer のレポートが主要なインターフェース。
- サブエージェントに親モデルを暗黙 inherit させない。常に Task の `model` を明示する（implementer のデフォルトは `cursor-grok-4.6-high`）。composer チャンクが基準未満なら、composer で反復せずそのチャンクを `cursor-grok-4.6-high` に再委譲する。
- 計画承認はハードゲート: ユーザーが計画を承認するまでファイル変更しない。承認後、まだ plan モードなら agent に SwitchMode してからオーケストレーションする。

## Cursor CLI tips

```bash
# 計画先行セッション（推奨エントリ）
agent --plan "/devflow <task description>"

# またはセッション途中で
# type: /devflow <task description>

# 並列 implementer の権限待ちを減らす
agent --plan --force "/devflow <task description>"
```
